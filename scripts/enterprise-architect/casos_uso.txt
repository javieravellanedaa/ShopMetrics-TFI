CU-001-001: Monitorear estado de las integraciones
Objetivo: Permitir al administrador del centro y al equipo de soporte verificar en tiempo real el estado de salud de todos los conectores POS y dispositivos IoT activos, identificando rápidamente las integraciones con problemas y tomando acción correctiva.
Descripción: El sistema presenta un panel consolidado con el estado de todas las integraciones (conectores POS y dispositivos IoT), indicando para cada una si está operativa, con advertencia o caída. Permite acceder al detalle de cada integración para diagnosticar problemas y reiniciar conexiones cuando corresponda.
Pre-Condición: El usuario está autenticado con rol de Administrador del Centro o de Soporte Técnico. Existe al menos un conector o dispositivo registrado en el sistema.
Post-Condición: El usuario obtiene una vista actualizada del estado de las integraciones. Si reinicia o reconfigura alguna integración, queda registrada la acción en el log de auditoría.
Actores Primarios: Administrador del Centro Comercial / Operador de Soporte Técnico
Actores Secundarios: Sistemas POS externos, dispositivos IoT físicos, sistema de monitoreo interno
Evento Disparador: El usuario accede al módulo Integraciones y selecciona la opción "Estado de las integraciones", o el sistema lo redirige automáticamente desde una alerta de integración caída.
Escenario principal de éxito
1. Usuario: Navega al módulo Integraciones y selecciona "Estado de las integraciones".
2. Sistema: Consulta el estado actual de todos los conectores y dispositivos registrados, recuperando el estado del conector (solo lectura, selector [verde/amarillo/rojo], se almacena) y el estado del dispositivo (solo lectura, selector [verde/amarillo/rojo], se almacena).
3. Sistema: Presenta un tablero con dos secciones (Conectores POS / Dispositivos IoT), mostrando para cada elemento un indicador visual de estado (solo lectura, selector [verde/amarillo/rojo], se almacena) y la fecha y hora de la última sincronización exitosa (solo lectura, fecha y hora, DD/MM/AAAA HH:MM, calculado, no se almacena).
4. Usuario: Identifica las integraciones con estado en advertencia o caída y hace clic en una de ellas para acceder al detalle.
5. Sistema: Muestra el detalle de la integración, incluyendo historial de errores recientes (solo lectura, texto, solo visualización), métricas de salud como cantidad de eventos recibidos en la última hora (solo lectura, numérico, >= 0, calculado, no se almacena) y latencia promedio (solo lectura, decimal, en milisegundos, calculado, no se almacena), y opciones de acción.
6. Usuario: Selecciona una acción correctiva (obligatorio, selector [reintentar conexión/reiniciar conector/suspender temporalmente la ingesta], no se almacena como tal).
7. Sistema: Ejecuta la acción seleccionada, actualiza el estado de la integración (calculado por el sistema, selector [verde/amarillo/rojo], se almacena) y registra la acción en el log de auditoría con acción (calculado por el sistema, texto, se almacena), recurso (calculado por el sistema, texto, se almacena), usuario (calculado por el sistema, identificador/UUID, se almacena como FK), fecha y hora (calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena) y hash de integridad (calculado por el sistema, texto, se almacena).
8. Sistema: Notifica al usuario el resultado de la acción correctiva mediante un mensaje (calculado por el sistema, texto, se almacena), tipo (calculado por el sistema, selector, se almacena), canal (calculado por el sistema, selector [push/email/WhatsApp], se almacena) y fecha y hora (calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena).
Caminos alternativos
CA-1. La acción correctiva no resuelve el problema.
CA-2. El usuario decide suspender temporalmente la ingesta de un conector.

CU-002-001: Registrar conector POS de un locatario
Objetivo: Habilitar la ingesta automatizada de datos de facturación de un locatario mediante la configuración del conector hacia su sistema de punto de venta, eliminando las cargas manuales en planillas y permitiendo el procesamiento de la información en tiempo real.
Descripción: El administrador del centro selecciona el sistema POS que utiliza el locatario, ingresa las credenciales y los parámetros de conexión, y el sistema valida la conexión y comienza la ingesta automatizada de los datos de facturación. Este caso de uso es el primer paso para habilitar la propuesta de valor central del producto: el cruce automatizado entre datos de tráfico y datos POS.
Pre-Condición: El usuario está autenticado en el sistema con rol de Administrador del Centro. El locatario al cual se le va a configurar el conector está dado de alta en la plataforma. Las credenciales del sistema POS del locatario están disponibles y autorizadas por el locatario.
Post-Condición: El conector POS queda registrado, validado y activo. El sistema comienza a ingestar los registros de facturación del locatario con la frecuencia configurada. Se registra la acción en el log de auditoría.
Actores Primarios: Administrador del Centro Comercial
Actores Secundarios: Locatario (provee credenciales y autorización), Sistema POS externo del locatario
Evento Disparador: El administrador navega al módulo Integraciones y solicita el alta de un nuevo conector POS para un locatario.
Escenario principal de éxito
1. Administrador: Accede al módulo Integraciones y selecciona la opción "Nuevo conector POS".
2. Sistema: Muestra el formulario con la lista de locatarios sin conector activo, presentando para cada uno el locatario (solo lectura, selector sobre listado precargado, se almacena como FK) con su nombre (solo lectura, texto, solo visualización) y rubro (solo lectura, texto, solo visualización).
3. Administrador: Selecciona el locatario al cual se asocia el conector (obligatorio, selector sobre listado precargado, se almacena como FK).
4. Sistema: Despliega la lista de tipos de POS soportados (obligatorio, selector sobre listado precargado [Fiserv/Bejerman/Tango Gestión/Geopagos/Aper/Maxirest/Fudo], se almacena).
5. Administrador: Selecciona el tipo de POS (obligatorio, selector sobre listado precargado, se almacena) y completa los campos de credenciales: URL del endpoint (obligatorio, texto, formato URL, se almacena), token o usuario y contraseña (obligatorio, texto, se almacena encriptada) e identificador de la cuenta del locatario (obligatorio, texto, se almacena).
6. Sistema: Valida la conexión contra el sistema POS externo realizando una llamada de prueba.
7. Sistema: Confirma que la conexión es exitosa, almacena las credenciales encriptadas (calculado por el sistema, texto, se almacena encriptada) y muestra el conector con estado (calculado por el sistema, selector, se almacena) en "Activo" y fecha de alta (calculado por el sistema, fecha, DD/MM/AAAA, se almacena).
8. Sistema: Inicia la ingesta automatizada de datos POS del locatario y registra la acción en el log de auditoría con acción (calculado por el sistema, texto, se almacena), recurso (calculado por el sistema, texto, se almacena), usuario (calculado por el sistema, identificador/UUID, se almacena como FK), fecha y hora (calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena) y hash de integridad (calculado por el sistema, texto, se almacena).
9. Administrador: Visualiza el conector con estado (solo lectura, selector, se almacena) en "Activo" en el listado de integraciones.
Caminos alternativos
CA-1. La validación de credenciales falla.
CA-2. El locatario aún no está autorizado a compartir datos.

CU-003-001: Registrar dispositivo IoT de conteo
Objetivo: Incorporar a la plataforma un dispositivo de hardware (cámara de visión computacional, sensor infrarrojo, antena WiFi tracking o barrera de estacionamiento) para que aporte datos de tráfico segmentados por zona del centro comercial.
Descripción: El administrador del centro registra un nuevo dispositivo IoT seleccionando su tipo y proveedor, ingresa los parámetros de conexión y vincula el dispositivo a una zona específica del centro. El sistema valida la conexión y comienza a ingestar los eventos de tráfico generados.
Pre-Condición: El usuario está autenticado con rol de Administrador del Centro. El dispositivo físico está instalado y conectado a la red del centro comercial. Las zonas del centro están previamente definidas en el sistema.
Post-Condición: El dispositivo queda registrado, validado y activo. El sistema comienza a ingestar los eventos de tráfico vinculándolos a la zona correspondiente. Se registra la acción en el log de auditoría.
Actores Primarios: Administrador del Centro Comercial
Actores Secundarios: Personal técnico del proveedor de hardware (en caso de configuración asistida), dispositivo IoT físico
Evento Disparador: El administrador accede al módulo Integraciones y solicita el alta de un nuevo dispositivo IoT.
Escenario principal de éxito
1. Administrador: Accede al módulo Integraciones y selecciona "Nuevo dispositivo IoT".
2. Sistema: Muestra el formulario de alta con los tipos de dispositivos soportados (obligatorio, selector sobre listado precargado [cámara Hikvision/cámara Axis/sensor V-Count/antena WiFi tracking/barrera Skidata/barrera Amano], se almacena).
3. Administrador: Selecciona el tipo de dispositivo (obligatorio, selector sobre listado precargado, se almacena) y el modelo específico (obligatorio, texto, se almacena).
4. Sistema: Despliega los campos de configuración correspondientes: dirección IP (obligatorio, texto, formato IPv4, se almacena), puerto (obligatorio, numérico, 1 a 65535, no se almacena), credenciales (obligatorio, texto, se almacena encriptada) e identificador del fabricante (opcional, texto, se almacena).
5. Administrador: Completa los datos de conexión y selecciona la zona del centro a la cual queda vinculado el dispositivo (obligatorio, selector sobre listado precargado, se almacena como FK).
6. Sistema: Realiza una conexión de prueba al dispositivo para validar que responde correctamente.
7. Sistema: Confirma la validación exitosa, registra el dispositivo con estado (calculado por el sistema, selector, se almacena) y fecha de alta (calculado por el sistema, fecha, DD/MM/AAAA, se almacena), y comienza a recibir eventos de tráfico con conteo (calculado por el sistema, numérico, >= 0, se almacena) y marca temporal ts (calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena).
8. Administrador: Verifica en la pantalla principal que los eventos de tráfico, con conteo (solo lectura, numérico, >= 0, se almacena) y marca temporal (solo lectura, fecha y hora, DD/MM/AAAA HH:MM, se almacena), comienzan a registrarse en tiempo real para la zona seleccionada (solo lectura, selector, se almacena como FK).
Caminos alternativos
CA-1. El dispositivo no responde al test de conexión.
CA-2. El dispositivo entrega un formato de datos no soportado.

CU-006-001: Configurar alerta basada en umbral
Objetivo: Permitir al administrador definir reglas de alerta sobre indicadores específicos (tráfico horario, ventas diarias, conversión por rubro, ocupación de estacionamiento) que se disparen cuando los valores cruzan el umbral configurado, habilitando una respuesta operativa inmediata.
Descripción: El administrador define una nueva regla de alerta seleccionando el indicador, la condición (mayor que, menor que, dentro de un rango), el valor de corte y los destinatarios que recibirán la notificación cuando la regla se cumpla. El sistema valida la regla y comienza a evaluarla en tiempo real.
Pre-Condición: El usuario está autenticado con rol de Administrador o de Gerente Operativo. Existen indicadores activos en el sistema (al menos un dispositivo IoT o un conector POS configurado).
Post-Condición: La regla de alerta queda registrada y activa. El sistema comienza a evaluar la regla contra los datos en tiempo real. Cuando se cumple la condición, se generan y despachan las notificaciones a los destinatarios indicados.
Actores Primarios: Administrador del Centro Comercial / Gerente Operativo
Actores Secundarios: Destinatarios de las alertas (otros usuarios del sistema), sistema de notificaciones
Evento Disparador: El usuario navega al módulo Alertas y solicita la creación de una nueva regla por umbral.
Escenario principal de éxito
1. Usuario: Accede al módulo Alertas y selecciona "Nueva alerta por umbral".
2. Sistema: Despliega el formulario de creación de regla con los campos requeridos: indicador (obligatorio, selector sobre listado precargado, se almacena como FK), condición (obligatorio, selector [mayor que/menor que/igual a], se almacena), valor de corte (obligatorio, decimal, > 0, se almacena) y estado (calculado por el sistema, selector, se almacena).
3. Usuario: Selecciona el indicador a monitorear (obligatorio, selector sobre listado precargado, se almacena como FK) desde el catálogo de indicadores disponibles, con su nombre (solo lectura, texto, se almacena) y unidad (solo lectura, texto, se almacena).
4. Sistema: Muestra los rangos típicos del indicador seleccionado (solo lectura, decimal, calculado, no se almacena), basados en el histórico del centro, como referencia para la configuración.
5. Usuario: Configura la condición (obligatorio, selector [mayor que/menor que/igual a], se almacena) con su valor de corte (obligatorio, decimal, > 0, se almacena), el período de evaluación (obligatorio, selector [por hora/diario/semanal], se almacena dentro de la condición) y los días de aplicación (obligatorio, selector múltiple [lunes a domingo], se almacena dentro de la condición).
6. Usuario: Selecciona los destinatarios de la alerta (obligatorio, selector múltiple sobre listado precargado, se almacena como FK) y los canales por los cuales se enviará (obligatorio, selector múltiple [push móvil/WhatsApp/correo electrónico], se almacena).
7. Usuario: Confirma la creación de la regla.
8. Sistema: Valida la consistencia de la regla, la activa actualizando su estado (calculado por el sistema, selector, se almacena) y comienza a evaluarla contra los datos en tiempo real.
9. Sistema: Registra la creación de la regla en el log de auditoría con acción (calculado por el sistema, texto, se almacena), recurso (calculado por el sistema, texto, se almacena), usuario (calculado por el sistema, identificador/UUID, se almacena como FK), fecha y hora (calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena) y hash de integridad (calculado por el sistema, texto, se almacena), y notifica al usuario que la alerta está activa mediante un mensaje (calculado por el sistema, texto, se almacena).
Caminos alternativos
CA-1. El usuario configura una regla con valor de corte fuera de los rangos históricos del indicador.
CA-2. El usuario intenta seleccionar un destinatario que no tiene los permisos necesarios.

CU-007-001: Recibir y gestionar alerta generada por Machine Learning
Objetivo: Habilitar la recepción y resolución de alertas de anomalías operativas generadas automáticamente por el modelo de Machine Learning, permitiendo al personal operativo responder rápidamente y al sistema mejorar continuamente la precisión de los modelos a partir del feedback recibido.
Descripción: El modelo de Machine Learning detecta una anomalía en el patrón de tráfico de una zona del centro y dispara una alerta. El operario recibe la notificación push en la aplicación móvil, accede al detalle, ejecuta un checklist guiado de verificación y registra la resolución (confirma anomalía, descarta o escala). El feedback del operario alimenta el reentrenamiento del modelo.
Pre-Condición: El operario tiene la aplicación móvil instalada y notificaciones push habilitadas. El modelo de ML está entrenado y activo. Existen al menos dispositivos IoT generando datos en tiempo real.
Post-Condición: La alerta queda en estado "Resuelta" con el detalle de la acción tomada y el tiempo de respuesta. El feedback del operario se almacena para mejorar la precisión del modelo en futuras evaluaciones.
Actores Primarios: Operario de Operaciones / Mantenimiento
Actores Secundarios: Modelo de Machine Learning (ejecución), Gerente del centro (supervisión), sistema de notificaciones push
Evento Disparador: El modelo de Machine Learning detecta una anomalía en el patrón de tráfico y dispara una alerta automáticamente.
Escenario principal de éxito
1. Sistema: El modelo de ML evalúa los datos de tráfico de la última ventana temporal (conteo de eventos de tráfico: solo lectura, numérico, > 0, se almacena en evento_trafico) y detecta que el indicador de una zona (zona: calculado por el sistema, selector sobre listado de zonas del centro, se almacena como FK; indicador: solo lectura, selector sobre catálogo de indicadores, se almacena como FK) está fuera del rango esperado con un nivel de confianza superior al umbral configurado (nivel de confianza: calculado por el sistema, decimal, 0.0 a 1.0, calculado, no se almacena en este paso; valor de corte del umbral: solo lectura, decimal, se almacena en regla_alerta).
2. Sistema: Genera una alerta con la información de la anomalía (tipo de alerta: calculado por el sistema, selector [umbral/ML], se almacena; zona: calculado por el sistema, selector, se almacena como FK; indicador: solo lectura, selector, se almacena como FK; valor observado: calculado por el sistema, decimal, calculado, no se almacena; valor esperado: calculado por el sistema, decimal, calculado, no se almacena; nivel de confianza: calculado por el sistema, decimal, 0.0 a 1.0, se almacena; severidad: calculado por el sistema, selector [baja/media/alta], se almacena; estado: calculado por el sistema, selector [abierta/en proceso/resuelta], se almacena; fecha: calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena; posibles causas sugeridas: calculado por el sistema, texto, solo visualización) y la encola para distribución.
3. Sistema: Envía la notificación push (mensaje: calculado por el sistema, texto, se almacena; tipo: calculado por el sistema, selector, se almacena; canal: calculado por el sistema, selector [push/email/WhatsApp], se almacena; fecha: calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena) a los operarios asignados a la zona afectada (usuario destinatario: calculado por el sistema, selector sobre usuarios con acceso al centro, se almacena como FK).
4. Operario: Recibe la notificación en su aplicación móvil y abre la alerta (identificador de la alerta: solo lectura, UUID, se almacena como FK).
5. Sistema: Muestra el detalle de la alerta (severidad: solo lectura, selector [baja/media/alta], solo visualización; estado: solo lectura, selector, solo visualización; fecha: solo lectura, fecha y hora, DD/MM/AAAA HH:MM, solo visualización), el gráfico del indicador con el momento de la anomalía resaltado (serie de conteo de tráfico: solo lectura, numérico, calculado, no se almacena), las posibles causas sugeridas (solo lectura, texto, solo visualización) y un checklist guiado de verificación (solo lectura, selector múltiple sobre listado precargado, solo visualización).
6. Operario: Ejecuta los pasos del checklist (ítems del checklist: solo lectura, selector múltiple sobre listado precargado [verificar escaleras mecánicas / verificar climatización / verificar pasillos bloqueados / verificar dispositivos IoT en la zona], solo visualización).
7. Operario: Registra el resultado de cada paso del checklist (resultado por ítem: obligatorio, selector [verificado/problema encontrado/no aplica], se almacena) y agrega comentarios (comentarios: opcional, texto, máx 500 caracteres, se almacena).
8. Operario: Marca la alerta como "Resuelta" indicando la causa identificada (causa identificada: obligatorio, texto, máx 500 caracteres, se almacena) y la acción tomada (acción tomada: obligatorio, texto, máx 500 caracteres, se almacena; estado: calculado por el sistema, selector [resuelta], se almacena).
9. Sistema: Almacena el resultado, calcula el tiempo de respuesta total (tiempo de respuesta: calculado por el sistema, numérico, en minutos, calculado, no se almacena) y registra la acción en el log de auditoría (usuario: calculado por el sistema, UUID, se almacena como FK; fecha: calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena; acción: calculado por el sistema, texto, se almacena; recurso: calculado por el sistema, texto, se almacena; hash: calculado por el sistema, texto, se almacena).
10. Sistema: Incorpora el feedback al pipeline de reentrenamiento del modelo (modelo de ML: solo lectura, selector, se almacena como FK; versión del modelo: solo lectura, texto, se almacena) para mejorar la precisión futura.
Caminos alternativos

CA-2. El operario no puede resolver la situación y necesita escalar.

Objetivo: Proveer al administrador del centro una estimación, generada por el modelo predictivo de Machine Learning, del riesgo de cierre de cada locatario en un horizonte temporal definido, permitiendo tomar acción correctiva antes de que la salida del locatario sea irreversible.
Descripción: El sistema ejecuta periódicamente el modelo predictivo de vacancia sobre la base de locatarios activos, calcula un score de riesgo y genera alertas cuando el score supera el umbral. Post-Condición: El administrador obtiene una vista del ranking de locatarios en riesgo. Si registra acciones de retención, estas quedan asociadas al locatario y al modelo para evaluación posterior del impacto.
Actores Primarios: Administrador del Centro Comercial / Gerente Comercial
Actores Secundarios: Modelo predictivo de Machine Learning, locatarios identificados (sujetos al análisis)
Evento Disparador: El usuario accede al módulo Analítica y selecciona la opción "Predicción de vacancia".
Escenario principal de éxito
1. Usuario: Navega al módulo Analítica y selecciona "Predicción de vacancia".
2. Sistema: Recupera del modelo predictivo (modelo de ML: solo lectura, selector, se almacena como FK; versión: solo lectura, texto, se almacena) el score de riesgo más reciente para cada locatario activo (score: solo lectura, decimal, 0.0 a 1.0, se almacena; locatario: solo lectura, selector, se almacena como FK; fecha de la predicción: solo lectura, fecha, DD/MM/AAAA, se almacena) y los ordena de mayor a menor riesgo.

4. Usuario: Selecciona un locatario del ranking para acceder al detalle (identificador del locatario: solo lectura, UUID, se almacena como FK).

Sistema: Almacena la acción asociada al locatario (acción de retención: calculado por el sistema, se almacena con FK a la predicción), programa el seguimiento (fecha de seguimiento: solo lectura, fecha, DD/MM/AAAA, se almacena) y registra la decisión en el log de auditoría (usuario: calculado por el sistema, UUID, se almacena como FK; fecha: calculado por el sistema, fecha y hora, DD/MM/AAAA HH:MM, se almacena; acción: calculado por el sistema, texto, se almacena; recurso: calculado por el sistema, texto, se almacena; hash: calculado por el sistema, texto, se almacena).
9. Sistema: Incorpora el dato al pipeline de evaluación del modelo (modelo de ML: solo lectura, selector, se almacena como FK), midiendo posteriormente si la acción fue exitosa (resultado de la acción: calculado por el sistema, booleano, calculado, no se almacena en este paso).
